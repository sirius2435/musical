本文件将用户提供的手册按原有 13 个主题重新排版，保留概念、适用条件、流程和页码索引。它是课程知识参考，不是新增代码禁令；没有附带或核验原始课件。具体原始要求见 [rules.txt](rules.txt)；V2 用户明确补充与本手册的差异见 [来源与冲突记录](sources-and-conflicts.md)。

## 1. 总体架构：一个功能如何贯穿整个系统

```text
用户操作
  → 前端页面与交互（React + TypeScript）
  → 需要服务器数据时，通过 API 发送约定的请求
  → 后端解析请求、执行业务逻辑、组织外部操作
  → 需要持久化时访问数据库
  → 后端整理响应，经 API 返回
  → 前端更新状态并重新渲染
```

贯穿项目的工具与原则：

- Git 管理代码变更、提交、分支与远端同步。
- Vite 是前端开发服务器与构建工具，不是业务逻辑层或版本管理工具。
- 模块化要求函数、组件、服务和数据边界具有清晰职责。
- 纯计算与副作用分离，让业务计算尽量可独立测试，数据库、网络和文件操作明确组织。

并非每次页面交互都需要后端或数据库。仅影响当前界面的操作可以只更新前端状态；需要跨用户、跨会话保存或访问服务器数据时，通常才需要 API、后端及持久化层。

## 3. 前端模块：页面、交互与状态

### 3.1 技术与职责

| 技术或概念 | 作用与适用场景 |
| --- | --- |
| TypeScript | 静态类型检查；定义数据结构、函数输入输出和组件 Props |
| React | 通过组件构建页面、表单、列表、卡片、按钮和弹窗 |
| 组件 | 按职责拆分导航栏、列表项、编辑器、统计区域 |
| 普通函数 | 独立表达筛选、排序、格式化、统计等计算 |
| Hooks / useState | 表单输入、开关、选中项、局部弹窗等组件状态 |
| Zustand | 管理多个组件或页面需要共享的状态 |
| useEffect | 在依赖变化时与外部系统同步或执行必要副作用 |
| Props | 父组件向子组件传递数据和回调 |
| Location / useLocation | 与页面导航相关的信息传递与读取 |
| CSS | 颜色、字体、尺寸、间距、边框等视觉样式 |
| Flexbox | 一维布局，如工具栏、行列排列和对齐 |
| CSS Grid | 二维布局，如卡片网格、仪表盘和矩阵 |
| Tailwind | 通过工具类组合间距、背景、圆角、布局等样式 |
| Vite | 本地运行、查看修改、构建前端资源 |

### 3.2 核心数据、展示型数据与常量

- **核心数据**：被用户或外部事件直接修改的事实，如编辑文本、选中项和页码。
- **展示型数据**：由核心数据计算得到，如过滤列表、统计数量和展示标题。通常直接推导，避免重复存储产生不一致。
- **常量**：当前语境下不变化的标签、固定配置，不需要响应式状态。

如果一个值能由已有状态稳定计算得到且无需独立修改，优先把它当作派生值。

### 3.3 Zustand 的常见访问方式

| 形式 | 含义 | 使用场景 |
| --- | --- | --- |
| getXXX() | 读取当前时刻的状态快照 | 普通逻辑一次性读取 |
| useXXX() | 在组件中订阅状态变化 | 展示内容需要随状态更新 |
| setXXX() | 更新 Store 状态 | 修改、保存和清空共享数据 |

组件需要重新渲染时使用响应式订阅。普通纯函数不调用 Hook，应显式接收数据。不把所有数据放进全局 Store，让局部状态留在使用它的组件中。每份共享状态有明确归属，避免多个模块随意修改。

这里的原整理内容只解释访问职责，没有规定具体 getter 名称或导出模板。V2 用户进一步要求 Store 尽量私有、get/use/set 职责清楚，并定位于跨页面核心状态；按 V2 执行，保留旧整理对“多组件或页面”的表述作为来源差异，不宣称已核验课件原文。

### 3.4 前端内部传递与服务端传输

| 方式 | 解决的问题 | 范围 |
| --- | --- | --- |
| Props | 父子组件传值 | React 组件树 |
| Location / useLocation | 导航时携带或读取信息 | 页面导航 |
| Zustand | 多组件或页面共享状态 | 前端内部 |
| API + JSON | 浏览器与服务器交换数据 | 前后端边界 |
| 服务 API + 数据格式约定 | 后端模块之间协作 | 服务间边界 |

Props、Location 和 Zustand 不会替代后端 API，也不会自动持久化数据。

### 3.5 前端实现流程

1. 明确页面区域，按职责拆分组件。
2. 用 TypeScript 定义核心数据、函数输入输出及 Props。
3. 决定状态归属；局部交互使用组件状态，确有共享需求时考虑 Zustand。
4. 编写事件和计算，核心状态变化后由 React 重新渲染。
5. 根据布局选择 Flexbox 或 Grid 等方式；在本课程项目中进一步遵守规则 55 的 Tailwind 要求。
6. 使用项目已有 Vite 配置运行并检查效果。

## 4. 后端模块：数据建模、业务计算与副作用

### 4.1 Scala 数据建模和结果处理

| 概念 | 作用与适用场景 |
| --- | --- |
| match | 根据值或数据形态进行分支处理 |
| Option[T] | 表达可选字段、查询可能无结果 |
| Try[T] | 表达可能抛出异常的计算成功或失败 |
| object | 单例组织，可包含程序入口 main |
| class | 定义需要实例化的数据与行为模板 |
| case class | 表达用户、订单、请求、响应等结构化数据 |
| enum | 表达有限状态、角色和分类 |
| abstract class | 定义需要子类实现的抽象基类 |
| trait | 定义可组合的能力或性质 |

建模的目标是明确数据含义。对于缺失或失败，用类型和分支表达，不默认值一定存在。介绍一种语言机制不代表所有业务代码必须使用它，也不构成禁止其他机制的依据。

### 4.2 纯函数与业务逻辑

纯函数相同输入得到相同输出，不直接修改外部状态，输入输出关系明确，便于独立测试。校验、筛选、转换、统计和价格计算适合独立表达。

尽量将核心业务计算与数据库、网络、文件操作分开，避免把所有规则和外部读写塞进一个大函数。对重要业务规则进行独立测试有助于降低修改风险。

### 4.3 副作用、Monad、IO 与 flatMap

| 概念 | 含义 |
| --- | --- |
| 副作用 | 与数据库、网络、文件等外部系统交互，或依赖外部状态 |
| 将副作用推到边缘 | 核心尽量纯计算，基础设施操作单独组织 |
| Monad | 某类计算的可组合结构，不是某个库的名称 |
| IO | 描述外部操作；构造 IO 描述通常不等于立刻执行 |
| flatMap | 串联存在数据依赖的计算 |
| Cats Effect / Fiber | 课程涉及的 IO 和轻量级并发机制 |

纯函数回答“算出什么”，IO 等机制组织“如何执行外部操作”。计算订单总价可以是纯函数；读取或保存订单属于外部交互。实现应遵守现有框架执行模型，不因本节概念就假定某框架已存在。

### 4.4 微服务边界与职责

服务说明名称、业务职责、负责的数据、公开 API 和协作约定。内部功能相关以保持高内聚，减少无必要依赖以保持低耦合，通过约定边界协作，避免依赖私有实现。

不要为微服务形式过度拆分简单项目。本项目规则 1–12 进一步明确：公开 API 消息和封装好的公开 Table 方法都是允许的调用边界；无需为了跨服务访问增加只做转发的接口。

### 4.5 后端典型处理流程

1. 接收请求，解析并进行必要校验。
2. 映射为明确类型，例如 case class。
3. 用纯函数执行可独立测试的计算。
4. 清晰组织数据库和网络等外部操作；课程语境涉及 IO / Monad。
5. 转换为约定响应并返回。

这是概念流程，不是完整可运行的 Web 后端模板。API 消息的具体形态由规则 20–33 规定。

## 5. 数据传输与 API：模块之间如何协作

### 5.1 微服务与 API 的区别

服务回答“哪个模块负责业务”，API 回答“其他模块如何调用”。API 应明确用途、请求字段及类型、响应字段及含义、非法输入与失败表达，以及双方如何保持契约一致。

具体 HTTP 方法、路由及错误码由项目需求和已有约定决定。该知识参考不自行规定课程未明确要求的协议。

### 5.2 序列化、反序列化、JSON 与 Circe

| 概念 | 含义 |
| --- | --- |
| 序列化 | 程序对象转换为 JSON 等传输或存储表示 |
| 反序列化 | 将 JSON 等表示解析为程序内结构 |
| JSON | 表达对象字段、数组等结构的文本数据格式 |
| Circe | Scala 生态中辅助 JSON 转换的库 |

例如，一个学生对象可以约定为：

```json
{"id": 1001, "name": "Alice", "age": 20}
```

这只是数据形态示意，不规定项目必须使用数字 ID。双方需要对字段、类型、语义达成一致。序列化不是加密，也不等于业务校验。JSON 是格式，Circe 是库。

### 5.3 数据传输流程

明确用途和输入输出 → 定义契约 → 发送方序列化 → 接收方解析与反序列化 → 执行业务 → 按约定返回结果 → 调用方更新状态或继续操作。

身份信任边界可以有意转换字段，例如外部 token 转内部 userId；见规则 28–29，不能为了字段相同而弱化鉴权。

## 6. 数据库：持久化与数据关系

### 6.1 关系型数据库基础

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| Table | 一类记录集合 | 用户表、订单表 |
| Row | 一条记录 | 某个用户 |
| Column | 记录字段 | 姓名、创建时间 |
| 数据类型 | 字段可保存的表示 | 整数、字符串、时间 |
| Primary Key | 唯一标识记录 | 用户 ID |
| Foreign Key | 引用其他表的键 | 订单关联用户 |

### 6.2 复杂类型存储

列表和自定义类不能默认原样放进字段。明确选用 JSON/text 序列化、拆分关系表或通过主外键关联。根据查询需求、数据库能力和项目设计决定，不将任何一种方式推广为通用答案。

### 6.3 数据库与后端边界

前端展示和收集操作，API 定义调用约定，后端按业务决定读写，数据库持久化和查询。通常由后端访问数据库，不让页面直接负责表读写。数据库不承担页面展示职责。

## 7. 工程工具：Git 与 Vite

### 7.1 Git 常见概念与命令

| 概念或命令 | 作用 |
| --- | --- |
| Repository | 项目及版本历史 |
| Branch | 独立开发工作线 |
| git clone | 获取远端仓库副本 |
| git pull | 获取并整合远端变更 |
| git status | 查看工作区与暂存状态 |
| git add | 将选定修改加入暂存 |
| git commit | 创建本地版本快照 |
| git push | 推送本地提交 |
| git merge | 合并分支 |

典型概念流程为检查状态、选择修改、创建提交，再按协作需要推送。add、commit、push 是不同操作；提交前检查选定内容。具体执行服从用户授权和项目流程。

### 7.2 Vite 与 Git 的区别

Vite 负责前端运行、反馈与构建，不管理业务规则、状态和历史。Git 负责记录变更、分支和回退，不运行页面或构建资源。

## 8. 端到端示例：保存一条日记

| 步骤 | 模块 | 处理内容 |
| --- | --- | --- |
| 1 | 前端 UI | 输入标题和正文，点击保存 |
| 2 | 前端状态 | 管理编辑值和必要状态；确有共享需求才考虑 Store |
| 3 | API / 传输 | 按约定发送保存请求 |
| 4 | 后端服务 | 接收请求并找到负责模块 |
| 5 | 业务逻辑 | 校验、转换、业务判断及缺失或失败处理 |
| 6 | 后端副作用 | 组织数据库写入 |
| 7 | 数据库 | 保存记录并返回结果 |
| 8 | 响应传输 | 序列化约定响应，调用方解析 |
| 9 | 前端更新 | 更新状态并显示保存结果 |
| 10 | 工程迭代 | 检查修改、预览界面、按工作流程保存版本 |

各步不强制使用特定库，实际代码应符合项目架构。

## 9. 调试时按模块定位

| 现象 | 优先检查 | 继续检查 |
| --- | --- | --- |
| 点击无反应 | 事件绑定、组件状态 | 控制台、渲染条件 |
| 输入不更新 | useState / Store 更新与订阅 | 直接修改对象、缺少订阅 |
| 没有请求 | 触发条件、地址、参数 | 网络面板、前端日志 |
| 请求失败 | 请求响应契约、入口、错误处理 | 服务日志、请求结构、序列化 |
| 后端结果错误 | 规则、映射、分支 | 纯函数测试、Option / Try 等结果处理 |
| 保存后未持久化 | 写入流程 | 连接、字段、事务和错误处理 |
| 数据保存但页面未更新 | 响应解析、状态更新与订阅 | 派生数据、渲染条件 |
| 样式错位、溢出 | 盒模型、Flexbox、Grid、工具类 | 父容器尺寸、间距、响应式 |
| 不确定修改内容 | git status 和差异 | 分支和提交记录 |
| 前端无法启动 | 脚本、依赖、Vite 配置 | README 和具体报错 |

先定位层次，再沿调用链检查，不同时盲改多个模块。

## 12. 给编程 Agent 的使用约定

1. 先检查 README、配置、依赖、目录和代码。
2. 尊重技术栈，不要求所有项目同时使用本文出现的库。
3. 按 UI、状态、API、业务和持久化职责组织，小项目不为形式过度分层。
4. 明确请求响应的字段、类型和语义，尊重已有契约及信任边界转换。
5. 区分可独立计算的业务与可追踪的外部操作。
6. 优先推导展示值，不重复维护同源状态。
7. 从现有配置确定并运行相关测试、类型检查、lint 或构建。
8. 围绕明确目标小步修改，检查差异和结果。
9. 不臆造框架、数据库、部署和协议等课程未规定的细节。
10. 本文是参考，不覆盖用户明确指令、项目规范或安全要求。

## 13. 复习与设计检查清单

- 能说明前端、后端、API、传输与数据库的职责。
- 能区分 React、TypeScript、Zustand、CSS/Tailwind 和 Vite。
- 能区分局部状态、共享状态、Props 和 Location。
- 能区分核心数据、派生展示数据与常量。
- 能解释纯函数、副作用、IO 与 flatMap。
- 能解释服务、API、高内聚和低耦合。
- 能区分 JSON、Circe、序列化与反序列化。
- 能解释表、行、列、类型、主键和外键。
- 能区分 Git 的暂存、提交、推送与 Vite 的运行构建。
- 能描述保存操作从前端经过服务和数据库再返回的完整流程。

实际开发时先定位所属模块，再读取对应概念；具体规范始终以用户采用的 60 条规则及明确修订为准。
