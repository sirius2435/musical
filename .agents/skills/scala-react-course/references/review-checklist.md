## 2. 严重程度与判定

| 级别 | 含义 | 示例 |
| --- | --- | --- |
| Critical | 违反核心架构/信任边界，破坏实际数据与调用责任 | 直接信任外部 userId、绕过表封装、业务多步操作使用错误连接造成部分提交 |
| Major | 违反明确课程编码规范或必需行为 | Scala var/传统 try 语法；API 泛型和执行入口错误；应更新的组件未订阅 |
| Minor | 可读性、命名和组织问题 | 不清晰命名、入口难以浏览、无收益拆分 |

严重程度不改变要求强度。对“尽量”“推荐”的偏离先说明实际影响，不能仅凭未用推荐形式就判强制违规；课件原件未核验标明来源 U/H，不伪称已核验。待确认与 Not run 单独列出，不冒充 Minor 缺陷。

## 3. Scala 语言风格

- **SL01 [Major，SC01–SC03]**：本次新增/修改 Scala 无 var、无命令式 for；集合变换优先 map/flatMap/filter，不用可变累加器绕过要求。搜索后查看语义，不把 IO for/yield 当循环。
- **SL02 [Major，SC04、SC08]**：缺失/失败有 Option/Either/Try 和明确分支；Try 不被误禁，也不被当成延迟 IO。对未处理的 get 检查实际失败路径。
- **SL03 [Major，SC06–SC07；R13–19]**：记录为 final case class/同名 codec，能力采用 trait 等合适结构；不同身份/有限状态不退化为任意字符串，也不强迫所有文本/数量包装。
- **SL04 [Major，SC05]**：Scala 新写或本次改写部分不使用传统 try/catch/finally；JDBC 释放改用已有合规封装或 Resource，不能仅删 finally。此禁令不用于 TS/Python。
- **SL05 [Minor，R15–18]**：类型与伴生对象同文件，重要对象独立、导入在顶部，枚举转换/codec 位于伴生对象；命名能表意。

## 4. 函数式编程

- **FP01 [Major，SC09–SC10；R13、22]**：核心校验/计算只依赖输入，时钟、随机、日志、数据库、文件和网络依赖没有隐藏在纯外观函数中。
- **FP02 [Major，R20–22]**：副作用确实在 IO 执行阶段发生；不存在 IO 构造前提前执行 JDBC、业务层自行运行 unsafe runtime 或把 Try 当 IO 的情况。
- **FP03 [Major，R9–12、22–23]**：map/flatMap/IO comprehension 清晰表达主步骤；不添加仅转发的 execute、Service 或通用 Context；真实复用逻辑可保留。

## 5. 后端架构

- **BA01 [Major，R1–6、34]**：服务位于 services 下、业务和表归属可说明，基础设施有系统服务归属；额外目录说明用途，不强制独立部署。
- **BA02 [Critical，R7–12、28–29]**：只跨服务调用公开 plan/封装好的 Table def；不访问私有 SQL、行映射、别的服务 utils 或绕过可信身份转换。
- **BA03 [Major，R8、12、32–33]**：utils 函数 private[所属服务]；路由只做分发、编解码和边界转换；服务注册列表在顶层合并。

## 6. 数据库与数据模型

- **DM01 [Major，R34–38]**：每表独立目录，Table 与 Initializer 分文件；建表、索引、约束在本表，启动处只组合初始化。
- **DM02 [Major，R13–19、24、29]**：领域、API 传输与数据库映射有明确归属；ID、枚举、日期、空值与响应外壳保持既有线格式，编解码不替代业务校验。
- **DM03 [Major，R7–8、36–38]**：每个 private xxxSql 紧邻对应公开 IO[T] 方法之前；绑定/执行/映射封装，公开方法不接任意 SQL、不泄漏 JDBC 结果集。
- **DM04 [Critical 或 Major，R22、37；BE03]**：相关写入复用传入连接；没有下层另开连接/提前提交导致部分写入。资源在成功、失败、取消时释放，事务按实际机制回滚；具体影响决定级别。

## 7. API 设计

- **AP01 [Major，R20–27、30]**：操作独立 Message 文件，final case class 构造参数承载输入，只有返回类型参数；plan(connection): IO[Response]；无输入用 NoRequestMessage，无空请求壳。
- **AP02 [Critical，R11、28–29]**：受保护注册实际执行 token 校验后构造可信身份；自报 userId 不能覆盖解析结果；合法身份仍检查具体权限。
- **AP03 [Major，R24、31–33、48–53]**：响应结构集中，名称统一推导、前后端匹配；服务级注册/顶层合并正确；内部 API 不需要前端镜像。class+send 是 R52 推荐，未采用不自动强制失败。
- **AP04 [Major，R22、28、31]**：真实成功/失败响应、过期 token、伪造身份和生产名称推导经过适用验证；未执行时报告验证缺口，而不是给出“全部合规”。

## 8. React 组件设计

- **RC01 [Major，FE01–FE03；R39–44]**：组件展示/事件、Hook 协调状态、纯函数转换职责可辨；不使用非响应式全局变量，展示数据由核心数据推导。
- **RC02 [Major 或 Minor，R41–47]**：复杂 index 直接展示有意义业务区域，不藏入万能 Layout；页面专用实现就近，递归拆分有复杂度理由，无行数阈值或形式化空目录。

## 9. Hooks 与状态管理

- **HS01 [Major，FE01–FE02；R42、60]**：常量不进入无必要 state，派生值没有另一份 state；核心更新后展示重算；effect 用来同步外部系统而不是复制派生值。
- **HS02 [Major，FE03–FE06]**：新增全局 Store 服务跨页核心状态，不滥用；尽量私有，get/use/set 职责明确；纯函数不调用 use，组件渲染不以 get 快照代替订阅。
- **HS03 [Major，R19、60]**：复杂请求页有 loading/ready/empty/error 及相关操作状态；小表单允许简单局部 pending/error，不强制庞大联合类型。
- **HS04 [Major，R60 的行为验证]**：重试、卸载和旧请求迟到不会造成不符合预期的覆盖；实际需要时处理重复提交；区分静态渲染与真实交互已测范围。

## 10. 项目组织

- **PO01 [Minor 或 Major，R3–4、39–47、54–59]**：新增目录表达用途；共享 UI 与页面业务分开；页面共享对象位置明确；无用资源经引用确认才清理，文档不混进源码。
- **PO02 [Major，R48–55]**：前端 API 按服务组织，通用发送/命名/token 在服务外按职责拆；Tailwind 为样式体系，必要 CSS 例外有依据。
- **PO03 [Major，G01]**：按任务语言和项目身份加载；Python、独立算法题、无关 TS 不被强加 Message/IO/React/Tailwind；不为套示例更换既有技术栈或无关配置。

## 11. 测试与运行验证

- **VR01 [Major，G03]**：读取真实构建配置并执行相关编译/typecheck/lint/tests/build，检查实际 diff；不虚构命令或通过结果，环境缺失明确 Not run。
- **VR02 [Major，G03]**：按变化选择鉴权/编解码/多步失败回滚/状态订阅等行为；区分 Mock、静态渲染、真实服务和独立 Agent 执行，不互相替代。
- **VR03 [Major，G03]**：包校验、Markdown/YAML/引用、原文哈希和 ZIP 内容单独记录；这些通过不能证明自动触发或代码生成遵循已通过。
